## 引言

交通仿真系统前端涵盖了三个核心的业务闭环：创建仿真任务、实时监控仿真运行、以及对历史仿真数据的可视化回放。本篇文档将深入拆解这三大核心功能的实现逻辑、关键技术难点和对应的源码结构，帮助开发者理解其在交互层和渲染层的具体工作原理。

## 交通仿真配置向导 (PISteps)

`PISteps.vue` 承担了创建复杂仿真任务的入口职责。由于交通仿真涉及路网地图、交通流分配、信号灯配时以及各类算法模型（跟驰、换道），一次性配置极易让用户产生困惑。因此，系统采用了分步向导（Wizard）的设计模式。

### 实现流程与状态管理

1.  **向导状态机 (`cur_step_num`)**:
    - 步骤 1：输入仿真名称。
    - 步骤 2：地图格式选择（txt/xml/osm）与文件上传。
    - 步骤 3：全局模型选择（跟驰、换道模型下拉框）、红绿灯周期配置（`signal_tabs`）、交通流OD矩阵配置（`road_tabs`，包含生成分布和转向比例）。
    - 步骤 4：插件配置（是否开启外部接管，如产生车辆）。
2.  **数据流转与验证 (`sim_info` & `control_views`)**:
    -   这是一个响应式的复杂对象，随着用户操作逐步填充。
    -   **关键点**: 在步骤切换时（如 `onBtnChangeStepClicked`），进行严格的数据校验。例如，在步骤 2 到 3 的切换中，验证地图是否上传成功；在步骤 3 到 4 的切换中，计算所有OD流量分布（`dist_percent_all`）的总和是否近似为 1.0（使用 `isAlmostEqual` 解决浮点数精度问题），以及各相位绿灯时间之和是否等于周期时间。
3.  **地图解析与预览 (`onUploadMapSuc`)**:
    -   地图上传成功后，不仅保存 `mapId`，还立即调用 `GetMapJson` 接口获取路网结构的 JSON 数据。
    -   **性能优化点**: `map_json` 对象非常庞大，通过 `markRaw(map_json_obj)` 将其标记为非响应式，避免 Vue 递归代理产生巨大的性能开销。
    -   随后调用遗留的 Canvas 工具 `generate_thumbnail`，在前端实时生成一张包含车道信息的路网预览图，展示在配置界面。
4.  **最终提交 (`onSubmit`)**:
    -   配置完成后，将庞大的 `sim_info` 和 `control_views` 对象序列化后存入 `sessionStorage`，并进行路由跳转至监控页（`startsimpi`）。这种方式解决了路由传参体积受限的问题。

## 实时仿真监控与控制 (SimPIView)

`SimPIView.vue` 是系统的实时监控大屏，它负责接收仿真引擎源源不断的数据流，并将其转化为直观的可视化界面。

### 核心机制分析

1.  **初始化与 WebSocket 连接**:
    - 页面加载时，从 `sessionStorage` 读取配置信息，初始化 Pixi.js 渲染引擎（`SimPIXI`）。
    - 建立与后端的 WebSocket 连接（例如：`/ws/frontend`），进行鉴权握手（`{"type": "backend", "ope": "hello"}`）。
    - 连接成功后，发送 `{"type": "eng", "ope": "start"}` 指令启动后端仿真计算。
2.  **高频数据流处理 (`sim_data` 事件)**:
    - 引擎每计算完一个仿真步（通常间隔很短），就会通过 WebSocket 推送一个包含所有动态元素的巨大的 JSON 对象。
    - **性能瓶颈与解决**: 解析如此庞大的 JSON 会阻塞主线程。前端通过遍历这些数据，调用 `SimPIXI` 的相关方法更新图形。
        - **增量更新**: 理论上最优的方案是后端只推送发生变化的元素。但在此实现中，前端通过比对车辆 ID（`sim_pixi.getVeh(veh.id)`），决定是新建精灵还是仅调用 `moveVeh` 更新坐标。
        - **旋转计算**: 根据车辆当前坐标和上一帧的坐标差异（`last_spd`），在 `moveVeh` 内部实时计算 `Math.atan2(y_diff, x_diff)`，并更新精灵的 `rotation` 属性，实现车辆平滑转弯。
3.  **交互与属性面板**:
    - `SimPIXI` 为每一辆车和每一个红绿灯相位开启了 `interactive` 模式。
    - 当用户点击某辆车时，触发回调，侧边栏或属性面板（`cur_obj_attr`）会实时显示该车的当前速度、所在车道（LaneID）、所在网格（CellID）和路由信息（Router）。

## 历史数据回放引擎 (SimReplayView)

`SimReplayView.vue` 解决了“如何复现过去”的问题。由于历史仿真可能包含数万个步骤和 GB 级别的数据，它在架构上与实时监控有着显著区别。

### 架构设计与长连接 (SSE)

1.  **数据流载体 - Server-Sent Events (SSE)**:
    - 与实时监控使用全双工的 WebSocket 不同，回放场景主要是服务端向前端单向源源不断地输送历史切片数据。因此采用了更轻量、基于 HTTP 的 SSE 协议。
    - **鉴权挑战**: 标准的 `EventSource` API 不支持设置自定义请求头（如 `Authorization: Bearer <token>`）。
    - **Fetch API 模拟 SSE**: 为了解决鉴权问题并支持跨域凭证（`credentials: 'include'`），前端使用了原生的 `fetch` API，通过读取响应的 `ReadableStream` (`response.body.getReader()`)，配合自定义的 `parseEventStream` 函数，手动解析 SSE 格式的文本流（解析 `event:` 和 `data:` 字段），从而实现了一个支持鉴权的 SSE 客户端。
2.  **回放控制总线 (Control API)**:
    - 除了数据流，前端还需要向后端发送控制指令。这通过一系列独立的 REST API 实现，如 `POST /replay/control/{sessionId}/{endpoint}`，支持的 `endpoint` 包括 `play`, `pause`, `stop`, `seek`, `speed`。
    - 例如，当用户拖动进度条（`el-slider`）触发 `onStepChange` 时，前端发送 `seek` 请求到特定目标步数；随后，后端的 SSE 流会跳过中间数据，直接推送目标步数之后的数据，并在前端触发 `seeked` 事件以同步当前进度条。
3.  **动态渲染与图层控制 (`updatePlaybackFrame`)**:
    - **坐标系对齐**: 回放数据中的 `x`, `y` 坐标必须与地图背景底图完全对齐。`SimPIXI` 提供了 `convertCoordinateX/Y` 方法，基于底图生成的偏移量（Padding 和 MinMax）将后端逻辑坐标映射到 Canvas 像素坐标。
    - **背景切换（图层控制）**: 用户可以通过开关（Switch）控制是否显示“道路标号”和“路口标号”。前端并非动态在 Pixi 中绘制这些文字（这会极大地消耗性能），而是利用旧版 Canvas 提前生成了四个不同版本的 Base64 背景图（无标号、仅道路、仅路口、全显示）缓存在 `bg_pics` 中。当用户切换开关时，瞬间替换 Pixi.js 容器底部的背景 `Sprite`，这是一种典型的以空间换时间的优化策略。
